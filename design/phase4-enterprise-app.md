# StarData 企业端产品设计（Phase 4）

> 版本：v1.0（设计稿，未实施）
> 决策基线：企业端 Web 应用（方向 B）；租户模型 = 单 org + 多数据域
> 范围：功能分布与产品设计层面的重构方案，不含具体实现代码

---

## 1. 背景与目标

### 1.1 现状问题

StarData 当前存在**两套前端承载同类能力**：

- `web-local`（`stardata start` 本地工具）：已定制双角色形态——业务门户（首页/对话/看板）+ 技术工作台（数据源/语义层/发布/需求回流），但只能在开发者本机运行，操作的是**本地项目文件**。
- `web-admin`（私有化部署控制台）：Rill Cloud 式项目页（Home/AI/Dashboards/Status/Settings + `-/edit` 在线编辑器），操作的是**已部署项目**，但信息架构面向多租户云服务，业务用户会暴露在 org/project/deployment 等技术概念下。

企业交付场景（如银行）中，技术治理者与业务使用者都只会通过浏览器访问部署环境，**不会在本机运行 CLI 工具**。因此双角色产品能力必须整体迁移到 web-admin。

### 1.2 目标形态

**一个应用，三个空间，三种角色：**

```
                  登录（Keycloak SSO）
                        │
        ┌───────────────┼────────────────┐
        ▼               ▼                ▼
    业务门户         技术工作台          平台管理
   （所有人）      （数据治理者）       （管理员）
   问数/看板      数据源/语义层/发布   成员/权限/系统
```

核心产品原则：

1. **业务用户零技术概念**：看不到 org / project / deployment / YAML / connector 等词汇，只接触「指标、维度、看板、对话、订阅」。
2. **语义层是唯一契约**：技术侧发布什么，业务侧才能问什么、看什么（发布门控）。
3. **需求闭环**：业务提问未被语义层覆盖 → 自动沉淀为工作台待办 → 技术侧补充语义 → 发布后业务侧即刻可用。
4. **web-local 废弃移除**：不再保留本地开发工具形态；门户/Studio 能力迁入 web-admin 后，web-local 包从构建与 CLI（`stardata start` 的 UI 入口）中下线。

## 2. 角色与租户模型

### 2.1 租户模型：单 org + 多数据域

- 部署初始化时创建**唯一 org**（如 `OCBC`），此后 org 概念对所有 UI 隐藏（URL 中保留仅作路由）。
- **project = 数据域**：按业务条线划分（如「零售业务」「对公业务」「风控合规」），每个数据域是一个独立的语义层 + 数据 + 权限边界。
- 对业务用户的呈现：数据域是看板与提问范围的「分类」，不是需要管理的对象。

### 2.2 角色模型

| 角色 | 对应现有权限 | 可见空间 | 典型用户 |
|---|---|---|---|
| 业务使用者 | project **viewer**（自带 UseAI） | 业务门户 | 业务经理、分析需求方 |
| 技术治理者 | project **admin**（manageProject） | 门户 + 技术工作台 | 数据工程师、BI 开发 |
| 平台管理员 | **org admin** | 全部三个空间 | IT 管理员 |

- 角色即落地页：登录后按最高权限决定默认页——业务使用者 → 门户首页；技术治理者 → 门户首页（顶栏多出「工作台」）；管理员 → 同上（多出「管理」）。
- 权限按数据域隔离：一个用户可以是 A 域的治理者、B 域的使用者（现有 project 级权限模型直接支持）。

### 3.2 全局导航

```
┌────────────────────────────────────────────────────────────────┐
│ [Logo StarData]   首页  对话  看板  │  工作台▾  管理▾    [🌐][👤] │
└────────────────────────────────────────────────────────────────┘
   ← 业务区（所有人可见）→        ← 按角色显隐 →
```

- **工作台▾**：下拉列出该用户有治理权限的数据域，选中后进入 `/studio/[domain]`；只有一个域时直接进入。
- **管理▾**：仅 org admin 可见。
- 空间切换即导航切换，不做整站换肤；延续现有 PortalNav 两段式（品牌栏 + Tab 栏）设计语言与 i18n（中英切换保留在右上角）。
- 移动端：业务门户三个 Tab 收入底部导航；工作台/管理不做移动端适配（桌面场景）。

## 4. 业务门户设计

### 4.1 首页 `/`

沿用 web-local 门户首页布局，数据源改为**已部署项目的已发布语义视图**：

```
┌──────────────────────────────────────────────┐
│              你好，想了解什么数据？              │
│        （副标题：用一句话提问，AI 帮你分析）      │
│  ┌────────────────────────────────────────┐  │
│  │ 🔍  各产品的交易金额是多少？        [→] │  │   ← 点击进入 /chat?new=true
│  └────────────────────────────────────────┘  │
│   (各产品交易金额?) (客户资产分布?) (营销转化率?) │   ← AI 推荐问题气泡
│                                              │
│  ┌───────────────┐  ┌───────────────┐        │
│  │ 💬 继续对话     │  │ 📊 我的看板    │        │
│  │ 最近: 交易分析… │  │ 3 个可用看板   │        │
│  └───────────────┘  └───────────────┘        │
└──────────────────────────────────────────────┘
```

- 推荐问题：聚合用户**有权限的全部数据域**的已发布语义视图生成（复用 `generateRecommendedQuestions`）。
- 空态：无任何已发布内容时显示引导文案；若用户同时是治理者，附「去工作台发布」链接。
- 多数据域时提问框旁提供数据域筛选（默认「全部」，实际路由到对应项目的 `-/ai`）。

### 4.2 对话 `/chat`

- 复用现有 `-/ai` 页面能力（会话列表 + 消息流 + 图表内嵌 + 工具调用过程折叠）。
- 从「项目下的 tab」提升为顶级导航；单数据域时直连该域 runtime，多数据域时会话创建前先选域（会话与域绑定）。
- **需求回流埋点（本期新增）**：当 AI 回答「无法用现有指标回答」或用户点踩时，弹出「提交数据需求」轻量表单（一句话描述），写入该域的 requests 待办 → 工作台「需求」页可见。
- 会话保留策略、删除会话沿用 runtime 现有 conversation API。

### 4.3 看板 `/boards`

```
┌── 看板 ──────────────────────────────────────┐
│  [全部] [零售业务] [对公业务]      🔍 搜索      │
│  ┌─────────┐ ┌─────────┐ ┌─────────┐         │
│  │交易分析  │ │客户资产  │ │营销效果  │         │
│  │零售业务  │ │零售业务  │ │对公业务  │         │
│  └─────────┘ └─────────┘ └─────────┘         │
└──────────────────────────────────────────────┘
```

- 只列**已发布**的 explore/canvas（发布门控过滤），按数据域分组/筛选。
- 卡片显示业务名称（display_name）与所属域，不显示资源类型等技术信息。
- 详情页 = 现有 explore 视图（时间范围、维度切片、导出遵循现有 feature flag 策略；exports 默认关闭）。
- 看板内保留「对此看板提问」入口（现有 explore 内 chat sidebar 能力）。

## 5. 技术工作台设计

工作台以**数据域**为操作单元，所有编辑发生在该域的 **dev 草稿区**，经「发布」后才影响业务侧（详见 5.4 与 §9 发布模型）。

### 5.1 总览 `/studio/[domain]`

沿用 web-local Studio 总览：四张指标卡（数据源数 / 语义视图数 / 已发布数 / 待处理需求）+ 待办列表 + 快捷入口。新增「最近发布记录」与「运行健康」摘要（来自 status 数据）。

### 5.2 数据源 `/studio/[domain]/sources`

- 连接列表：名称、类型（DuckDB/ClickHouse/Postgres/文件…）、状态、引用它的语义视图数。
- 接入向导（沿用 web-local sources 页 + web-common connector 表单）：选类型 → 填连接参数 → 测试连接 → 保存（落为 dev 草稿区的 connector YAML + 凭证走项目环境变量）。
- 文件类数据源（CSV/Parquet）支持浏览器直接上传（落到项目 data 目录）。

### 5.3 语义层 `/studio/[domain]/semantics`

工作台核心页，沿用 web-local 向导式编辑器：

- 列表：语义视图名、业务名称、维度/度量数、发布状态（草稿/已发布/已修改未发布）。
- 编辑器（`semantics/[name]`）：左侧表单向导（选模型/表 → 定义维度 → 定义度量 → 时间设置 → 业务名称与描述），右侧实时 YAML 预览；保存写入 dev 草稿区。
- 「高级编辑」跳转 IDE 直接改 YAML（同一文件，双向一致）。
- AI 辅助（沿用 runtime 已有 generate metrics-view 能力）：从表结构一键生成语义视图初稿。

### 5.4 发布 `/studio/[domain]/publish`

发布门控从「publish.yaml 标记过滤」升级为**真正的发布动作**：

```
┌── 发布 ──────────────────────────────────────────┐
│  待发布变更（dev 草稿区 vs 生产）                    │
│  ● 语义视图「交易分析」已修改      [查看差异]        │
│  ● 新增数据源「客户主数据」                          │
│  ● 看板「营销效果」新增                             │
│                                                  │
│  发布范围勾选 ☑☑☐          [发布到生产]            │
│──────────────────────────────────────────────────│
│  发布历史：v12 2025-06-01 张工 「新增交易语义」 [回滚] │
└──────────────────────────────────────────────────┘
```

- **发布 = dev 草稿区文件打包为新 archive asset → redeploy 生产部署**（复用 Phase 3 的 assets 本地存储 + TriggerRedeploy 链路）。
- 发布历史 = archive asset 版本序列，支持回滚（指回旧 asset 重新部署）。
- publish.yaml 门控标记保留，控制「已部署但不对业务可见」的灰度场景。

### 5.5 需求 `/studio/[domain]/requests`

- 沿用 requests-file 待办机制：来源（Chat 自动回流 / 业务手动提交）、状态（open/处理中/完成/拒绝）、关联会话上下文链接。
- 处理动作：「去补充语义」直接跳到对应语义视图编辑器；完成后可通知提交人（远期，先做状态流转）。

### 5.6 高级模式 `/studio/[domain]/ide`

- 即现有 `-/edit` 工作区（文件树 + WorkspaceDispatcher + 血缘图 + connector 面板），定位为专业用户逃生舱。
- 与向导编辑器操作同一份 dev 草稿区文件，无同步问题。

### 5.7 运行状态 `/studio/[domain]/status`

现有 `-/status` 迁入：资源列表与健康状态、数据刷新（refresh 触发）、部署日志、（管理员可见）环境变量。

## 6. 平台管理设计

| 页面 | 内容 | 现有基础 |
|---|---|---|
| 数据域 `/settings/domains` | 创建/重命名/归档数据域（=项目），显示各域资源规模与最近发布时间 | web-admin 项目 CRUD ✅，术语改造 |
| 成员 `/settings/members` | 邀请用户（对接 Keycloak）、用户组、按域分配角色（使用者/治理者）、移除 | org/project members + usergroups ✅ |
| 智能配置 `/settings/ai` | LLM 供应商/模型/密钥、连通性测试 | 目前在 .env（部署级），先做只读展示，可写留远期 |
| 系统 `/settings/system` | 品牌 Logo、默认语言、审计日志 | 部分能力散落，远期整合 |

- 创建数据域流程简化为：填名称 → 立即可进工作台接数据源（Phase 3 已打通空项目 → archive 部署链路，创建后首次发布即自动建立部署）。
- 隐藏/移除多租户云残留：计费、org 切换、public project、request access 等入口在企业端一律不出现。

## 9. 功能分布与代码模块映射

### 9.1 前端

| 模块 | 动作 |
|---|---|
| **web-common** | 承接迁移：portal 组件（首页/推荐问题/publish-store/requests-file/boards 卡片）、studio 向导页（sources/semantics/publish/总览卡片）、PortalNav/Tabs 导航壳从 web-local 直接迁入（作为 web-admin 的组件库，无需兼容双端）。现有 WorkspaceDispatcher、chat、explore 已在 web-common 无需动 |
| **web-admin** | 新增三个路由组：`(portal)`（首页/chat/boards 顶级导航）、`(studio)`（挂到项目上下文，复用 `-/edit` 的 runtime 连接与 FileAndResourceWatcher 基建）、`(settings)`（现有 org/project 设置页收敛改造）；登录后角色落地逻辑；导航重构 |
| **web-local** | **移除**：组件迁走后从 npm workspace、构建链与 CLI embed 中摘除；`stardata start` 不再作为产品入口（命令可保留为纯 runtime 调试模式或直接下线，实施时定） |

### 9.2 后端（admin / runtime）

| 能力 | 现状 | 缺口 |
|---|---|---|
| dev 草稿区（在线编辑持久化） | `-/edit` 依赖 editable dev deployment + git 回写 | **核心缺口**：archive 项目需支持 dev instance 文件编辑落盘 + 读取（方案：dev deployment 使用可写副本，编辑经 runtime file API 写入） |
| 发布 = 打包 + redeploy | assets 本地存储 ✅、TriggerRedeploy ✅ | 新增 admin API：将 dev instance 当前文件打包为 archive asset 并指到 prod（含发布历史记录） |
| 发布历史/回滚 | asset 表已存版本 | 新增按项目列出 asset 版本 + 指定 asset 重新部署的 API |
| 需求回流存储 | requests.yaml 文件方案（web-local） | 沿用文件方案（随项目走、发布无关），Chat 侧新增写入入口 |
| 权限 | org/project 角色齐备 ✅ | 无缺口，纯前端映射 |
| 文件上传数据源 | runtime file API 支持 | 上传大小与类型限制策略 |

### 9.3 与既有形态的兼容

- 现有 `/[org]/[project]` 路由与 ProjectTabs 保留（内部/运维仍可用），新导航是其上的企业化包装；不破坏 CLI deploy 链路——CLI 上传视为一次「外部发布」，同样产生 asset 版本。
- GCS/多 org 等后端上游能力路径不删除；前端移除 web-local 会显著降低与 Rill 上游的可合并性，已接受该代价（项目已深度 fork）。

## 10. 关键技术依赖与风险

| # | 风险 | 影响 | 对策 |
|---|---|---|---|
| R1 | **archive 项目的 dev 草稿区可行性未验证**（`-/edit` 的 git 回写假设不成立） | 决定 4b 全部工作的技术方案 | 实施前先做 1-2 天技术验证（spike）：dev deployment + runtime 文件写 API + 打包发布最小闭环 |
| R2 | 发布打包的原子性（发布瞬间业务侧查询中断） | 业务体验 | redeploy 本身是新 instance 就绪后切换；验证切换窗口，必要时前端做发布中提示 |
