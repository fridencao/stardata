基于 Rill 开源架构的自研「智能问数 + 智能 BI」技术方案

保留 Rill 的语义层 / BI-as-Code / Agent-native 新架构，在 UI 与操作上做企业化优化，并自研增值的"智能问数"大模型层。

基础：Rill（Apache-2.0 开源） POC 基座：StarData 项目（已本地跑通） 文档版本：v1.0 · 2026-07-25

0结论先行（给评审看）

能做，而且推荐做。Rill 是 Apache-2.0，允许修改、再分发、闭源商用。其"语义层 + 声明式建模 + Agent-native"架构，恰好是"智能问数"最稳的底座——让自然语言映射到指标维度，而不是裸写 SQL，从源头规避幻觉与口径不一致。

推荐路线：以 Rill 开源核心作"数据 / 语义层引擎"，自研两层——① 智能问数 Agent（接你们自己的大模型）；② 企业化 UI（更简单的问数入口、移动端、嵌入与分享/审批）。两层通过 Rill 的 API / MCP 打通。这样架构最干净、IP 最清晰、增值点全在你手里。

唯一要在自研里补齐的：Rill Cloud 的托管式 AI 不在开源仓，问数 Agent 的 LLM 编排需自行实现（这恰是你们最值钱的部分）。

4语义层设计（架构皇冠，先把它立住）

语义层用声明式 YAML 定义"维度 / 度量 / 时间粒度"，Git 版本化。它是人和 Agent 的唯一口径源。StarData 项目里已有一份可直接复用的范例：

metrics/account_mart_metrics.yaml（节选）

version: 1
type: metrics_view
display_name: 客户经营概览
model: account_mart          # 星型模型（事实+维度 JOIN）
timeseries: date
smallest_time_grain: "day"

dimensions:                  # 维度
  - name: region        expression: region
  - name: product_category  expression: product_category
  - name: risk_level   expression: risk_level
measures:                    # 度量（受约束的计算）
  - name: sum_txn_amount  expression: "sum(txn_amount)"   # 交易金额(万元)
  - name: txn_count       expression: "count(*)"
  - name: active_customers expression: "count(distinct customer_id)"
  - name: new_customers   expression: "count(*) filter (where is_new = 1)"
为什么它是"护栏"：问数 Agent 不直接生成裸 SQL，而是只从这份语义层里挑维度与度量。即便 LLM 出错，也只会"选错指标"，而不会"删表 / 越权 / 口径漂移"。这比传统 NL2SQL 稳一个数量级，也是 Rill 研究的结论之一。

进阶：语义层可向上与司内指标平台双向同步（指标定义一处维护、处处一致），向下约束引擎与 Agent——形成你们的数据治理中枢。

5智能问数 Agent 流程（你们的增值核心）

① 用户中文提问→ ② NL 理解 + 意图识别→ ③ 实体链接：术语/同义词归一→ ④ 映射到语义层维度&度量→ ⑤ 生成受约束查询→ ⑥ 取数 + 自动选图→ ⑦ 回答 + 图表 + 引用
  1. NL 理解：用你们自有大模型（如司内大模型 / Qwen / 混元等）做语义解析，输出结构化"意图 + 约束"。
  2. 实体链接：用领域词典把"存款""对公客户"等业务黑话映射到语义层标准名，解决中文同义问题。
  3. 语义层映射：仅允许从 metrics 的维度/度量集合中取值，拒绝任何语义层外的字段——这是护栏生效的关键一步。
  4. 受约束查询：生成的是对语义层（或 Rill API / MCP）的调用，而非裸 SQL；必要时回退到带权限的受限 SQL。
  5. 取数 + 自动选图：经 Rill 引擎取数，按数据类型自动选柱状/趋势/占比图，并附"用了哪些指标"的可点击引用。
  6. 多轮与追问：基于上下文做下钻、同比环比、归因（可接 Rill 的 Explain 式异常归因思想）。
  7. 权限贯通：问数与取数全程继承语义层的行级权限，确保"不同人问同一句话，看到的数不同"。
与 Rill 开源的关系：Rill 自带 MCP Server 与 Agent 指令（StarData 已生成 .mcp.json + .claude/），可作为你们 Agent 与数据之间的"标准接缝"。你们在此之上叠加中文优化、领域词典、多轮、私有 LLM 与司内治理即可。

7落地路线：A（Fork）vs B（Rill 作引擎 + 自研）

A. Fork 开源核心，改 UI + 加 Agent

✅ 上手最快，直接站在源码肩上进

  • ❌ 需长期维护 fork、跟随快速迭代的上游（v0.88 刚发）
  • ❌ 与上游差异越大，合并越痛
  • ❌ 品牌/合规需剥离 Rill 痕迹

B. Rill 作引擎 + 自研 UI/Agent 推荐

✅ 架构最干净、IP 最清晰

  • ✅ 增值点（问数 Agent、企业 UI）全在你们掌控
  • ✅ 通过 API / MCP 解耦，Rill 可随版本平滑升级
  • ⚠️ 需定义清晰的接口契约（语义层 Schema、查询 API）
建议：以 路线 B 为默认，但 POC 阶段可直接 fork 跑通以加速验证；接口稳定后再收敛到"Rill 引擎 + 自研前后端"。两者在"语义层"上完全兼容，切换成本低。
