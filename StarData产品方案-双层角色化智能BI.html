1. 背景与问题

StarData 的能力底座已经具备：中文 Chat BI 端到端跑通（DeepSeek + 结构化答案 + 图表 + 引用 + 同比环比）、数据源接入与测试连接、指标中文别名（label_cn）、自托管认证。但当前的界面组织仍然偏工程师——配置与使用混在同一套偏技术的界面里（YAML 指标、表名、/-/settings 这类 dev 风格路由），业务人员一进来面对的是空白 chatbox 和一堆技术概念。

核心判断：问题不在"功能不够"，而在"角色没分层、语义层没产品化"。业务人员不是不能用，而是没有一条为他们设计的、零配置的入口。解法是把"配置"和"使用"拆成两个有清晰契约的表面，并用语义层作为两者之间的契约层。

2. 产品定位与目标角色

一句话定位：面向企业的"业务自助问数 + 技术治理配置"双层智能 BI——技术建好"业务数据字典"，业务对着字典用自然语言聊天。

角色典型用户核心诉求
业务使用者
Business		分析师、运营、业务线负责人、管理层不问技术细节，只关心"我想知道什么"，要的是可信任的答案、图表、看板与预警。
技术治理者
Tech / Admin		数据工程师、平台 admin、IT把数据接进来、把口径定义清楚、把指标发布出去、管好权限，让业务"问得出来、问得对"。
设计原则：两个角色共用同一份语义层，但看到的是两套不同的界面与心智模型。技术侧强调"治理与发布"，业务侧强调"引导与信任"。

3. 核心概念模型

三个贯穿全产品的概念，是这套方案的"骨架"：

  • 语义层 = 业务词汇表。技术定义的指标/维度，经 label_cn 转成业务能说的人话。这是 Chat BI 的"可用边界"，也是天然的答案护栏（只回答词汇表内的事）。
  • 发布门控（Publish Gateway）。指标默认是草稿，技术点"发布"后才对业务可见。既避免业务问到半成品，也给了技术清晰的"交付"动作。
  • 需求回流（Demand Backflow）。业务问了词汇表没覆盖的东西，系统不报冷错，而是"已向管理员发起配置请求"，把需求自动回流成技术的待办。

4. 信息架构（双角色导航树）

建议采用同一应用、按角色切换导航与首页（而非独立 portal），降低基础设施成本，也契合 StarData 当前单应用的形态。登录后按 OIDC group/role 决定默认落地页与可见导航。

4.1 技术工作台 Tech

工作台 / (默认落地)
├─ 概览          配置健康度："业务现在能问什么"
├─ 数据源         连接器列表 · 新增 · 测试连接 (#36 已落地)
├─ 语义层 / 指标   指标与维度定义（可视化编辑器，替代手写 YAML）
├─ 发布管理       草稿 → 已发布 · 版本 · 回滚
└─ 成员与权限      OIDC 用户/组 · 角色分配

4.2 业务智能问数 Business

智能问数 / (默认落地)
├─ 首页           推荐问题 · 我的看板 · 团队共享 · 最近
├─ 对话           Chat BI（结构化答案卡 + 追问 + 下钻）
├─ 我的看板       保存的问答 / 看板卡片
└─ 订阅与预警     周期推送 · 阈值告警

5. 关键页面与交互设计

5.1 业务首页（零空白页进场）

最大的劝退点是空白 chatbox。业务首页分三块：

  • 为你推荐的问题：从已发布指标反推。例如已发布「销售额 / 订单量」→ 建议"本月销售额同比如何？""各区域订单量排名？"
  • 我的看板 / 团队共享：同事或自己保存的问答卡片墙，点开即续聊。
  • 最近与热门：部门内高频问题，降低"从零开始"的焦虑。
复用：已有的结构化答案（summary/body/insights/followUps/charts）与追问 chips（#25）直接作为对话页核心；首页只是它的"引导外壳"。

5.2 对话页（Chat BI）

  • 答案卡：结构化 JSON 渲染为「摘要 + 正文 + 洞察 + 图表 + 引用」。
  • 追问 chips：点选即续问（已建）。
  • 下钻："解释这个数字""为什么下降"→ 触发同语义层内的根因探索。
  • 口径透明：每答案附"统计口径说明 + 数据更新时间"，建立信任。
  • 未覆盖兜底：词汇表外的提问 → 友好提示 + 自动发起配置请求（见 3 需求回流）。

5.3 技术概览（配置健康度）

一屏告诉技术："现在业务能问什么、还缺什么"。指标包括：已接入数据源数、已发布指标数、近 7 天业务提问命中率、未覆盖提问 Top N（= 需求回流输入）。这是技术与业务之间的"状态面板"。

5.4 语义层可视化编辑器

替代部分手写 YAML，降低非 Rill 专家技术的门槛：选数据源 → 自动探测表/字段 → 勾选要暴露的指标 → 填中文名（label_cn）→ 设口径与单位 → 存为草稿。这里生成的仍是底层 metrics YAML，只是给了一层可视外壳。

5.5 发布管理与需求回流面板

  • 发布：草稿 → 已发布，支持版本与回滚；发布后业务词汇表即时更新。
  • 需求回流：业务问不到的问题在此聚合成待办列表，技术一键"去定义"跳转编辑器，定义完发布即闭环。

6. 角色与权限模型

能力业务使用者技术治理者
问数 / 看板 / 订阅✅ 仅基于已发布指标✅
数据源 / 语义层 / 发布🚫 不可见✅
成员与权限🚫✅（admin）
发起配置请求✅（需求回流）✅ 接收并处理

同一账号可同时具多角色（按 OIDC group 映射）。Phase 1 已规划 Keycloak/OIDC，本方案直接复用其 group/role 作为角色来源。

7. 发布流程与数据流

技术侧：  接入数据源 → 定义指标(草稿) → 测试连接(#36) → 发布 ─┐
                                                              ↓
语义层：  业务词汇表（已发布指标集）◀── 发布门控 ◀──────────┘
                                                              ↓ 驱动
业务侧：  首页推荐问题 → 对话问数 → 图表/洞察/引用 → 保存看板/订阅
                                                              ↓ 未覆盖
需求回流：业务提问未命中 → 自动配置请求 → 技术待办 → 定义并发布 → 闭环

9. 实施路线图

A

信息架构与角色切换（低成本、高感知）

同 app 内按角色切换导航与默认落地页；业务默认进「智能问数」，技术默认进「工作台」。复用现有路由，主要是导航壳与首页分流。

B

业务首页引导 + 发布门控

业务首页三块（推荐/看板/最近）；指标加 draft/published 状态与发布动作；首页推荐问题由已发布指标反推。

C

语义层可视化编辑器（接入向导）

选数据源 → 探测字段 → 勾选指标 → 填中文名 → 存草稿。可视化外壳生成底层 YAML。

D

需求回流 + 看板/订阅/预警

未覆盖提问聚合成技术待办；业务可保存看板、订阅周期推送、设阈值告警。

10. 待确认问题

Q1. 两个角色是同一 app 内切换，还是独立 portal？
本方案默认"同 app 内角色切换"（低成本），但独立 portal 在重度隔离场景更干净，需定。
Q2. 业务侧是否严格限定"仅已发布指标可问"，还是允许试探未发布？
建议默认严格限定（护栏 + 需求回流），但可配置为宽松模式。
Q3. 看板 / 订阅的存储与权限粒度？
个人 vs 团队共享、组织级可见性，影响存储模型，需与 Phase 3 运维方向对齐。
Q4. 是否需要多组织 / 多空间（workspace）？
若面向多租户企业客户则需，单组织内可暂不。
